# RoboTwin benchmark

Static benchmark description, task inventory, and "how to use" walk-through. Regenerated by the `benchmark-env-generator` skill; manual edits will be overwritten. For reproducibility see [`install.md`](install.md); for skill-run + smoke-test log see [`history.md`](history.md).

## About

RoboTwin is a **dual-arm bimanual-manipulation imitation-learning benchmark** built on **SAPIEN 3.0.0b1**, targeting tabletop object manipulation with two 6-DOF arms plus parallel-jaw grippers. It ships **50 task modules** under `envs/*.py`, selectable via `--task_name`. The framework does **not** expose a gym-style `step(action) -> (obs, reward, done, info)`; instead each `envs.<task>` class inherits `envs._base_task.Base_Task` (itself a `gym.Env` subclass) and exposes:

- `take_action(action, action_type={"qpos","ee","delta_ee"})` — applies a dual-arm action tensor to the simulator (no return value).
- `get_obs()` — returns a dict with `joint_action.vector` (flat qpos for both arms), RGB+depth camera streams, and proprio state.
- `check_success()` — boolean success judgement used as the sole evaluation signal. There is no shaped reward.

Classification: **IL** (imitation learning). The `benchmark-env-generator` classifier scored 0/8 on RL-readiness auxiliaries (no `gym.register`, no VecEnv, no shaped reward YAMLs, no in-tree algorithms/).

## Action, observation, reward

| Field | Value |
|-------|-------|
| Default action type | `qpos` (joint position) |
| Action dimension (nominal) | **14** per step (7 per arm = 6 DOF + 1 gripper) |
| Execution | Chunked — the policy server returns `{"actions": [T, 14] float32}`; `script/robotwin_run_utils.py::execute_policy_action_chunk` iterates the T rows and calls `take_action` on each. |
| Observation | dict of `joint_action.vector`, `observation.head_camera.rgb/depth`, `observation.left_camera.rgb`, `observation.right_camera.rgb`, `pointcloud`, `instruction`. See `script/robotwin_policy_obs.py::robotwin_obs_to_policy_dict`. |
| Reward | None (IL benchmark). Evaluation is `TASK_ENV.check_success() -> bool`. |
| Episode length | Per-task step limit in `task_config/_eval_step_limit.yml` (range 400–1700). |

The test server `tests/test_random_policy_server.py` advertises `action_dim=14` in its handshake metadata; if you introduce an embodiment with a different qpos layout, pass `--action_dim N` to the server.

## How to use

All commands assume the headless container is up (`docker compose -f docker/docker-compose.headless.yaml up -d`).

### 1. Start a policy server

Either a real trained policy that speaks `policy_websocket` (openpi, LIBERO/robocasa-style), **or** the bundled random-action smoke server:

```bash
docker exec -d robotwin-headless bash -lc \
  'cd /workspace/RoboTwin && python tests/test_random_policy_server.py --port 8000 --action_dim 14'
```

### 2. Pick a task

From the inventory table above; smallest step-limit tasks (e.g. `beat_block_hammer`, `adjust_bottle`, `click_bell`) are quickest for smoke runs. Pass it to the clients via `--task_name`.

### 3. Single-episode rollout (`scripts/run_demo.py`)

```bash
docker exec robotwin-headless bash -lc \
  'cd /workspace/RoboTwin && python scripts/run_demo.py \
     --task_name beat_block_hammer --task_config demo_clean \
     --policy_server_addr localhost:8000 \
     --num_resets 1 --log_dir ./logs --save_video'
```

Writes:

- `logs/demo/beat_block_hammer--<ts>/demo.log` (stdout tee, flushed per line).
- `logs/demo/beat_block_hammer--<ts>/demo.mp4` (side-by-side head/left/right camera stitch, 10 fps, H.264).

### 4. Multi-episode eval (`scripts/run_eval.py`)

```bash
docker exec robotwin-headless bash -lc \
  'cd /workspace/RoboTwin && python scripts/run_eval.py \
     --task_name beat_block_hammer --task_config demo_clean \
     --policy_server_addr localhost:8000 \
     --n-episodes 50 --log_dir ./logs --save_video'
```

Writes:

- `logs/eval/beat_block_hammer--<ts>/eval.log` — per-episode line with rolling success rate, then a `FINAL RESULTS` block.
- `logs/eval/beat_block_hammer--<ts>/episode_{000..049}_success={True|False}.mp4` — one MP4 per episode.

### 5. Other task configs

`task_config/*.yml` defines head camera resolution, embodiment, and render settings. Common values: `demo_clean` (deterministic scene), `demo_randomize` (domain randomisation). Pass via `--task_config`.

### 6. Swap embodiments

Embodiments are defined in `task_config/_embodiment_config.yml` and task YAMLs override them via the `embodiment` list. Dual-arm Piper (the default) produces `action_dim=14`; mixed-arm configs can differ. Clients read the true dim from `obs["joint_action"]["vector"]` at runtime, so as long as the policy server's handshake `action_dim` matches the env's live dim, rollouts work.
